# M1 event ingestion prototype

Requires Node 24 LTS, pnpm 10.20.0 and OpenCode 2.x. In a checkout run `pnpm install --frozen-lockfile`, `pnpm build`, and `pnpm test`. `pnpm build` emits a bundled Node executable entry point at `dist/apps/daemon/src/main.js` with migrations and connector assets under `dist`; `pnpm typecheck` performs the separate strict typecheck. The Python specification suite is separate; see `.github/workflows/spec-validation.yml` for its dependencies.

Register a source and project with `pnpm exec tsx apps/daemon/src/main.ts register source_example project_example`. Use locally chosen opaque IDs (8Ã¢â‚¬â€œ128 letters, numbers, underscore or hyphen); a source is bound to one project. Start the daemon in a terminal with `pnpm exec tsx apps/daemon/src/main.ts start`. It stays in the foreground. In another terminal use `pnpm exec tsx apps/daemon/src/main.ts doctor` or `pnpm exec tsx apps/daemon/src/main.ts stop`. Data, discovery, and token are under `%LOCALAPPDATA%/.adaptive-harness` on Windows or `$HOME/.adaptive-harness` on POSIX. The HTTP service listens on an ephemeral loopback port. Stopping uses an authenticated request, not an unverified PID signal.

On Windows, install into a project with `./packages/connectors/opencode-v2/install.ps1 -Project <project-directory>`. Create `.opencode/adaptative-harness.json` inside that project with `sourceInstanceId`, `projectId`, `discoveryFile` and `tokenFile`; the two file paths point to `daemon.json` and `token` in the state directory. Paths stay local; the file contains no token. See the connector README. Uninstall using `uninstall.ps1 -Project <project-directory>`; modified plugin files are preserved. Restart OpenCode after installation.

Events contain allowlisted metadata only. Tool inputs, outputs and prompts are not sent. OpenCode 2.2.5 provides the same native call `id` to before/after hooks; its hash is stored as the span ID, together with an allowlisted tool name. An explicit native `error` is mapped to failed; `completed` remains unknown because a completed shell tool can report a non-zero exit. The connector drops events on errors or after its bounded in-flight limit; no durable spool or retries exist. Diagnostic counts are best effort. Process termination can lose outstanding asynchronous sends.

## Verification and limitations

On Windows 11, OpenCode 2.2.5 direct CLI (`--standalone`, `openai/gpt-6-luna`) ran one shell command exiting 1 and a separate successful command. With this daemon active, SQLite contained two `tool.started` and two `tool.completed` rows with distinct event IDs; outcome was absent on all four. A separate direct CLI task completed with the daemon stopped. A separate T3 Code 0.1.6 UI run on Windows 11 used OpenCode 2.2.5 with `openai/gpt-6-luna` in a disposable project. The agent attempted to read a missing file, then successfully read a synthetic fixture. SQLite recorded two `tool.started` and two `tool.completed` events, four distinct event IDs, one hashed session identifier and four initial jobs; all outcomes and call spans were absent. After stopping the daemon between turns, the same session read the fixture again and completed. The offline events were not persisted. These observations do not establish child-agent lineage, outcome or per-call correlation, daemon crash recovery under load, Linux behavior, installer safety on POSIX, or security of all Windows ACL and concurrent-start edge cases. Do not treat this prototype as production-ready until those gaps are closed. A bounded durable spool with visible loss accounting is the next increment.

If events do not arrive, verify the project-local plugin path `.opencode/plugins/adaptative-harness/index.ts`, IDs and token/discovery paths, run doctor, and confirm source registration. Check connector diagnostics without copying tokens or tool output into reports. A `403` means the source/project binding does not match; `409` means an event ID was reused with different content. Version and launcher evidence must be recorded separately for T3.

The daemon uses an authenticated identity handshake and an exclusive startup lock. A stale lock fails closed and must be removed manually after verifying no daemon is running. The lock is not an automatic crash-recovery lease. On Windows the state directory and newly written discovery/token files are checked for a current-user-only ACL; installations and inherited permissions outside this directory are not covered by this check.

On 2026-11-02, a direct Windows OpenCode 2.2.5 / GPT-6 Luna probe of the revised connector observed separate hashed spans for a missing-file read and a successful read. The native error mapped to `failed`; the completed read remained unknown. A separate nonzero-exit shell invocation also remained unknown, since native completed does not establish command success. Callback field names came from the OpenCode 2.2.5 SDK and the earlier sanitized native capture; no tool input or output was retained in the event records.

## Linux container validation (2026-11-02)

Docker Desktop 4.93.0 / Engine 29.8.1 on Windows 11 ran the pinned Debian Bookworm container described in [the Linux test README](../../tests/linux-opencode/README.md), with Node 24.22.2 and OpenCode 2.2.5. A scripted local model fixture requested two real native read-tool calls: missing file then existing file. The plugin persisted four metadata-only events, two hashed spans and four initial jobs. Both native callbacks and SQLite rows were checked. The test then verified completion with the daemon stopped, persistence and renewed ingestion after restart, and continuation when the daemon stopped between tool calls. The second call's events were dropped during interruption; no replay was observed or claimed. Four scenarios passed; no model credentials or external network were used. This does not establish authenticated-model, native host Linux, T3-managed Linux, crash recovery, or interruption during a single tool call.
